# Руководство разработчика

Основа веб-платформы для продуктовых A/B-тестов по [исходному описанию](../ExperimentLab.md).

**Статус:** работают конфигурация и жизненный цикл экспериментов, планирование выборки, неизменяемые версии CSV, Experiment Health с SRM, сравнение двух пропорций и Welch t-test. Автоматические отчёты, bootstrap и CUPED — следующие этапы.

## Быстрый запуск

Требуются Node.js 22.12+, Python 3.12+ и [uv](https://docs.astral.sh/uv/getting-started/installation/). Docker для локального запуска не нужен.

Из корня проекта:

```sh
npm ci
uv sync --frozen
npm run db:migrate
npm run db:seed  # необязательно: три демонстрационных черновика
npm run dev
```

- Интерфейс: http://127.0.0.1:5173
- API и интерактивная спецификация: http://127.0.0.1:8000/docs
- Liveness: http://127.0.0.1:8000/health
- Readiness (доступ к таблице экспериментов): http://127.0.0.1:8000/ready

SQLite создаётся миграцией в `experimentlab.db` в корне. База и окружения исключены из Git. Настройки работают по умолчанию; для переопределения скопируйте `.env.example` в `.env`. Все команды выполняются из корня репозитория.

## Что уже есть

- Обзор со счётчиками из базы, список с поиском, фильтрами и пагинацией.
- Создание и редактирование черновика: гипотеза, метрика, группы, α, ожидаемый относительный эффект, мощность, базовая конверсия, единица рандомизации и даты.
- Переходы draft → running → completed; при запуске сохраняется неизменяемый статистический план, дальнейшее редактирование запрещено сервером.
- Расчёт выборки в форме, карточке и связанном калькуляторе; результат хранится в эксперименте.
- CSV по одному пользователю на строку, проверка конкретных строк, полные неизменяемые версии, история и скачивание исходных файлов с проверкой SHA-256.
- Защита от устаревших сохранений и конкурентных изменений через версию записи.
- Experiment Health: пропуски, повторы ID, пересечение и размеры групп, SRM по сохранённому плану; ошибки и предупреждения разделены.
- Анализ бинарных/непрерывных метрик: групповые оценки, абсолютный и относительный эффект, p-value, ДИ и допущения; без автоматического победителя.
- Страница будущего модуля отчётов.
- Валидация на сервере, общий формат ошибок, состояния загрузки и ошибок в UI.
- SQLAlchemy, миграции Alembic, явная повторяемая загрузка демоданных.
- OpenAPI и генерируемые из него TypeScript-типы, lock-файлы, тесты и GitHub Actions.

## Работа с экспериментом и CSV

1. Создайте черновик и заполните план. Черновик разрешено сохранять незаполненным.
2. Для текущего расчёта и запуска нужны бинарная метрика, группы 50/50, единица «Пользователь», базовая конверсия, положительный ожидаемый относительный эффект, мощность и обе даты. Причины недоступности запуска видны в карточке.
3. Запустите эксперимент из карточки. Все параметры и рассчитанная выборка фиксируются; сохраняются фактическое время запуска и снимок плана. Даты плановые, автоматического перехода по времени нет.
4. Загрузите CSV в карточке или разделе «Данные». Загрузка разрешена в любом статусе пользовательского эксперимента. В демо пользовательские файлы не загружаются.
5. Завершите running-эксперимент из карточки. Обратные переходы и пропуск running запрещены.

Формат [примера CSV](../examples/user_metrics.csv): `user_id,variant,metric_value`. Кодировка UTF-8 (BOM допустим), разделитель — запятая, колонки можно переставлять. `variant` строго `control` или `treatment`. Платформа получает готовое назначение групп и не рандомизирует пользователей.

ID непустой и уникальный во всём файле; повтор пользователя между группами также ошибка. Для конверсии/retention допустимы только 0 и 1; для выручки — конечные неотрицательные числа с десятичной точкой. Пропуски, NaN/Infinity и неверные типы отклоняются. Лимиты по умолчанию: **10 МиБ**, **100 000 строк данных**, до **100 ошибок** в ответе с номерами физических строк. Одна наблюдаемая группа принимается с предупреждением, без статистического вывода.

Каждая загрузка — самостоятельный полный снимок, не добавка к предыдущему. Пользователи могут повторяться между версиями. Ошибочный файл целиком отклоняется; успешная версия сохраняет исходные байты, SHA-256, размер, счётчики групп, время и снимок конфигурации. После первой загрузки метрику и единицу рандомизации менять нельзя, чтобы не переинтерпретировать данные.

Файлы лежат в `storage/datasets/` под сгенерированными именами, метаданные — в БД. Путь и лимиты настраиваются через `.env.example`. Каталог исключён из Git; для сохранности данных резервировать нужно **и БД, и каталог файлов**. После завершения можно импортировать новые снимки, при этом зафиксированный план не меняется.

## Проверка качества и анализ

В истории каждой версии есть ссылки «Проверки качества» и «Сравнить метрики». На `/health` и `/analysis` можно выбрать эксперимент и версию вручную. В URL зафиксирован ID версии; новая загрузка не подменяет результат. Калькулятор размера выборки находится на `/planning`.

Расчёт повторно читает исходный файл, проверяет SHA-256 и метаданные и использует план, сохранённый **на момент загрузки**, включая allocation и α. Последующее редактирование черновика не переинтерпретирует старую версию. Если на момент загрузки план не был зафиксирован запуском, результат помечается как исследовательский.

Блокируют сравнение: пропуски, дубли пользователей, пересечение групп, неверные значения, отсутствие группы, нарушение целостности/метаданных и обнаруженный SRM. Недостаточный объём для SRM, незрелость D7, промежуточная выгрузка и недостигнутая плановая выборка показаны как предупреждения. Отсутствие SRM не доказывает качество данных. Импорт по-прежнему отклоняет некорректные строки; Health отдельно повторяет проверки сохранённых файлов.

Z-test использует объединённую дисперсию и двусторонний p-value, интервал абсолютного эффекта — Newcombe–Wilson. Welch не предполагает равные дисперсии. Расчёт доступен и для исследовательских непрерывных метрик/неравных размеров групп, хотя планировщик запуска пока ограничен бинарным сценарием 50/50. Пограничные случаи возвращают явные причины и `null`, без NaN/Infinity и фиктивного p-value. Автоматических выводов о победителе нет.

## Команды разработки

| Команда | Действие |
| --- | --- |
| `npm run dev` | API и frontend; Ctrl+C останавливает оба процесса |
| `npm run dev:web` / `npm run dev:api` | Запуск одного приложения |
| `npm run check` | TypeScript, production-сборка frontend и Python-тесты |
| `uv run ruff check .` | Проверка Python-кода |
| `npm run format:check` | Проверка форматирования frontend |
| `npm run format` / `uv run ruff format .` | Форматирование frontend / Python |
| `npm run api:types` | Экспорт OpenAPI и обновление TypeScript-типов |
| `npm run db:migrate` | Миграция базы до последней версии |
| `npm run db:seed` | Добавление отсутствующих демонстрационных черновиков |
| `uv run alembic -c backend/alembic.ini revision --autogenerate -m "description"` | Создание новой миграции для последующей проверки |
| `uv run alembic -c backend/alembic.ini check` | Проверка расхождений моделей и миграций |

После изменения API обновляйте спецификацию и типы, затем выполняйте проверки. CI проверяет, что сгенерированный контракт не устарел. `npm run build` создаёт `apps/web/dist`; для его размещения нужен SPA fallback на `index.html` и reverse proxy `/api`, `/ready` к backend. Путь frontend `/health` должен открывать SPA, это страница качества данных. Технический liveness API доступен отдельно на порту 8000. Vite proxy действует только при разработке.

## PostgreSQL

Для общей среды можно использовать PostgreSQL вместо SQLite. В `.env` задайте пароль и URL подключения (спецсимволы в пароле URL-кодируйте):

```dotenv
POSTGRES_PASSWORD=replace-with-your-local-password
EXPERIMENTLAB_DATABASE_URL=postgresql+psycopg://experimentlab:replace-with-your-local-password@127.0.0.1:5432/experimentlab
```

```sh
docker compose up -d postgres
npm run db:migrate
npm run db:seed
npm run dev
```

Это создаст отдельную базу PostgreSQL; SQLite автоматически не переносится. Конфигурация Compose содержит только сервис БД, приложения запускаются локально. Тесты по умолчанию используют временный SQLite; проверка PostgreSQL описана в плане развития.

## Текущие границы

Запуск с рассчитанной плановой выборкой пока поддерживает бинарную метрику, 50/50 и пользователя. Welch и сравнение метрик при неравных фактических размерах групп доступны отдельно для загруженных снимков. CSV на пользователя не применяется к кластерной рандомизации. Полноту выгрузки, окно наблюдения и зрелость retention по этим трём колонкам установить нельзя. Bootstrap, CUPED, последовательный анализ, поправки на множественные сравнения и автоматические отчёты ещё не реализованы. Завершение эксперимента само по себе не подтверждает статистическую значимость.

Аутентификация и разграничение доступа пока отсутствуют: текущий запуск рассчитан на локальную разработку. Объектное хранилище для нескольких инстансов и фоновые импорты — следующие инфраструктурные шаги.
