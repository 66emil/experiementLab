# Этапы 5–9: интерфейсы и план реализации

**Сейчас реализована только презентационная оболочка.** Новые страницы — интерактивные макеты с синтетическими значениями, отдельной навигацией и постоянной пометкой `UI PREVIEW`. Они не создают AnalysisRun, не выполняют bootstrap/CUPED, не сохраняют параметры и не экспортируют отчёты. Рабочие функции этапов 1–4 доступны отдельно.

## Посмотреть локально

После `npm run dev` откройте http://127.0.0.1:5173/preview.

| Этап | Экран | Что можно посмотреть сейчас |
| --- | --- | --- |
| 5 | `/preview/runs` | Историю, снимок конфигурации, порядок проверок и причины блокировки |
| 6 | `/preview/analytics` | Выбор контекста, сравнение групп, ДИ, распределения и ограничения |
| 7 | `/reports` | Документ и статический образец Markdown демонстрационного запуска |
| 8 | `/preview/bootstrap` | Форму параметров, иллюстрацию интервала и предлагаемый бюджет |
| 9 | `/preview/cuped` | Контракт ковариаты, список проверок и иллюстрации корректировки |

В первых трёх экранах переключаются пять состояний: готовый результат, отсутствие запусков, блокировка качества, ошибка вычисления и неполный результат. Состояние отражается в query-параметре `scenario`; например, `/preview/analytics?scenario=partial`. Это сценарий макета, а не ответ сервера.

Селекторы данных и запуска синхронизированы между собой. Поля bootstrap меняют только локальное состояние; фиксированная иллюстрация не пересчитывается. Кнопки запуска, применения и экспорта отключены с объяснением.

## Граница реализации

Код находится в `apps/web/src/features/preview/`, загружается отдельными чанками через lazy-маршруты и использует локальные типизированные fixtures. Здесь нет API-клиента, вызовов статистического пакета или записи в хранилище браузера. Глобальная оболочка проверяет `/ready`: индикатор относится к доступности текущего API, а не будущих модулей.

Схема БД, миграции, OpenAPI, CSV-контракт и статистический движок не меняются. Текущий `/analysis` остаётся расчётом по запросу: его результат **не является сохранённым AnalysisRun**. Ссылка в карточке эксперимента ведёт на общий макет без передачи пользовательских данных.

## 5. Воспроизводимый запуск анализа — следующий этап

Будущая сущность AnalysisRun:

| Поле / группа | Назначение |
| --- | --- |
| Эксперимент, ID/версия датасета, SHA-256 | Однозначная привязка исходных данных |
| Неизменяемая конфигурация | Метрика, распределение, α, мощность, эффект, рандомизация, даты, правило остановки и статус фиксации плана |
| Метод и параметры | Название, версия, альтернатива, метод ДИ; для bootstrap — B, seed и RNG |
| Версия движка и зависимостей | Воспроизведение в определённом окружении |
| Время и статус | Создание, начало и окончание с явным временем UTC |
| Снимок Health | Ошибки, предупреждения и ограничения на момент запуска |
| Результат и диагностика | Групповые оценки, эффект, p-value/ДИ или причина их отсутствия |

Предлагаемый процесс: проверить принадлежность датасета эксперименту → целостность версии и снимок плана → Health → применимость метода и бюджет → вычисление → сохранение результата. Блокировка объясняется конкретной причиной, без статистических результатов. SRM нельзя использовать как единственное подтверждение качества.

История добавляется без перезаписи прошлых результатов. Повтор после ошибки создаёт новый запуск. Редактирование черновика или новая загрузка не меняет старые снимки. Для исследовательского плана сохраняется предупреждение.

Будущему API нужны создание запуска, список истории и чтение конкретного запуска. Окончательная схема маршрутов будет определена при реализации; сейчас этих endpoint нет.

**Критерии следующего этапа:** сервер проверяет связь и качество; история переживает перезапуск; результаты неизменяемы; расчёт использует сохранённые данные/параметры; карточка показывает реальные доступные действия и результат.

## 6. Analytics Dashboard — следующий этап

Источник — сохранённый AnalysisRun, без повторного расчёта при открытии. Эксперимент ограничивает доступные версии, версия — подходящие запуски. Результат и предупреждения относятся к одному контексту.

Показывать размеры групп, значения метрик, абсолютный/относительный эффект, метод, ДИ и p-value. Если поле отсутствует, показывать причину и `—`, без подстановки нуля. При нулевой контрольной метрике относительный эффект остаётся неопределённым согласно политике движка.

Для бинарной метрики подойдёт сравнение долей, для непрерывной — распределения с одинаковыми границами интервалов и график ДИ эффекта. Сводки графиков должны сохраняться с запуском или воспроизводиться из его неизменяемого датасета по версионированному правилу.

Временная динамика требует корректной семантики времени, часового пояса, окна наблюдения и полноты периодов. Порядок строк и дата загрузки не являются временной осью метрики. Макет объясняет отсутствие такого графика.

**Критерии:** контексты не смешиваются; обработаны пустые/заблокированные/ошибочные/неполные результаты; отсутствующие интервалы не подменяются; предупреждения видны рядом с оценками; графики соответствуют данным запуска.

## 7. Отчёт конкретного запуска — следующий этап

Просмотр и Markdown-экспорт будут использовать одну модель отчёта, построенную из сохранённого AnalysisRun: гипотеза, конфигурация, версия/хеш данных, качество, метод/параметры, движок, групповые оценки, эффект, ДИ, p-value и ограничения. Источник и версия правил отчёта сохраняются для воспроизведения без подмены текущими настройками эксперимента.

Прозрачные правила интерпретации:

- При блокировке не формировать вывод об эффекте.
- При отсутствии p-value/ДИ объяснять причину и не делать вывод о значимости.
- Значимость оценивать по сохранённому α и методу; p-value не является вероятностью истинности гипотезы.
- Практическую ценность оценивать отдельно по **заранее заданному** порогу. Если порог находится внутри ДИ, его достижение не подтверждено.
- Отсутствие значимости не доказывает отсутствие эффекта. Эквивалентность требует отдельного дизайна и метода.
- Не объявлять победителя автоматически; указывать ограничения фиксированного горизонта и множественных сравнений.

В статическом примере p = 0,011 при α = 0,05; эффект +6,15 ₽ (+3,34%), ДИ [1,42; 10,88] ₽. Порог +5% от 184,20 ₽ равен 9,21 ₽ и находится внутри ДИ. Числа иллюстрируют правила и **не рассчитаны** новым механизмом.

**Критерии:** просмотр и экспорт согласованы; тот же запуск и версия шаблона дают то же содержимое; текущий план не меняет старый документ; неполные результаты не получают готовых продуктовых выводов.

## 8. Bootstrap разности средних — следующий этап

Предлагаемый метод — двусторонний **percentile bootstrap** разности `mean(treatment) − mean(control)`. Группы ресэмплируются независимо с возвращением, сохраняя их размеры. Границы ДИ — квантили α/2 и 1−α/2 распределения разностей. Percentile выбирается явно: default SciPy — BCa. Описание алгоритма: [официальная документация SciPy bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html).

Планируемые настройки: B = 10 000 по умолчанию, seed, алгоритм/версия RNG, уровень доверия, правило квантилей, порядок данных и версии зависимостей. Один seed без фиксации алгоритма и окружения недостаточен для долговременного воспроизведения.

Предлагаемый бюджет: 1 000 ≤ B ≤ 50 000 и `B × (n_control + n_treatment) ≤ 100 000 000`, пакетная обработка без матрицы всех ресэмплов, ограничения времени и памяти на сервере. Это проект ограничений, пока они не действуют; профиль уточняется измерением нагрузки.

Условия: независимые наблюдения и группы, подходящая единица рандомизации, репрезентативность данных. Bootstrap не исправляет смещение, зависимость или недостаток информации малой выборки; кластерам нужен другой ресэмплинг. Минимальный размер, постоянные группы, вырожденный интервал, переполнение и нулевой control требуют документированной политики. Не выводить p-value из наличия нуля в ДИ: отдельный bootstrap-тест здесь не запланирован.

**Критерии:** независимые эталоны, повтор с тем же seed/окружением, граничные случаи и ресурсные лимиты, сохранение параметров в AnalysisRun, выбор только для совместимых метрик.

## 9. CUPED — следующий этап

Область первого метода: непрерывная Y и одна числовая ковариата X, измеренная **до воздействия** на той же единице рандомизации. Корректировка: `Y_adj = Y − θ × (X − mean(X))`; оценка общего θ и последующий вывод будут зафиксированы при реализации. Предэкспериментальные данные могут снизить дисперсию, но улучшение не гарантировано. Первоисточник: [Deng, Xu, Kohavi, Walker, WSDM 2013](https://ai.stanford.edu/~ronnyk/2013-02CUPEDImprovingSensitivityOfControlledExperiments.pdf).

Предлагаемое расширение CSV:

```csv
user_id,variant,metric_value,covariate_value,covariate_period_end,assigned_at
u001,control,184.2,168.0,2026-10-18T23:59:59Z,2026-10-19T00:00:00Z
u002,treatment,190.3,172.5,2026-10-18T23:59:59Z,2026-10-19T00:00:00Z
```

**Это проект формата, текущий импорт его отклонит.** Базовые три колонки должны остаться допустимыми для текущих методов. CUPED потребует полного набора дополнительных полей; пропуски не заменяются нулём и не удаляют пользователей скрыто.

Проверять тип/конечность X, покрытие обеих групп, уникальность пользователя, ненулевую дисперсию, совместимость метрики и рандомизации. Для дат — часовой пояс и `covariate_period_end < assigned_at`. Начало/длина предпериода и полнота агрегата задаются отдельными метаданными импорта. Политику отсутствующего подтверждения предпериода нужно определить до реализации; предполагать его корректность по умолчанию нельзя.

Нельзя автоматически доказать происхождение X, достоверность внешних дат, отсутствие утечки будущего или влияния treatment, одинаковые окна и корректность соединения источников. Это условия метода, требующие подтверждения владельцем данных. Порядок дат не доказывает происхождение значений.

**Критерии:** старый CSV работает; неполная/постоянная/постэкспериментальная ковариата обрабатывается явно; есть независимый эталон; θ, центрирование, контракт предпериода, диагностика и версия метода сохраняются; исходные и скорректированные оценки различимы в интерфейсе и отчёте.
